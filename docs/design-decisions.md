# 八个关键设计取舍

按 ADR（Architecture Decision Record）的写法记录：决策 / 备选方案 / 为什么否掉备选。

记录"否掉了什么"往往比记录"选了什么"更有用：后者看代码就知道，前者只能靠文档传承。

---

## ADR-1 评分权不交给模型

决策：五维评分由 `evals/rubric.py` 中的确定性规则计算，模型只做语义诊断与改写。

备选：让模型按 rubric 描述自行打分（这是最常见的做法）。

否掉的理由有三条：

1. 偏袒自己。模型倾向于给刚生成的内容高分（self-preference bias），
   反思循环会因此提前"自认为达标"而停止，收敛变成假装收敛。
2. 不可复现。换个温度、重跑一次分数就变，CI 里无法断言，回归测试失去意义。
3. 不可解释。模型给不出"为什么是 73 而不是 78"，复盘时没有价值。

把打分权拿走后，模型可以去做真正需要语义理解的工作。副产品是一个很强的性质：
分数的变化必然可归因到某个指标的变化。

---

## ADR-2 离线确定性后端是产品的一部分

决策：实现一个完整的 `MockBackend`，让全链路无需 API Key 即可运行。

备选：只写单测用的桩；或者要求使用者自备 Key。

否掉的理由：

- 评审者第一次接触项目时，不应该先配 Key 才能看到任何东西。零参数 `demo` 跑通，是这个项目能被验证的前提。
- 离线后端让 CI 覆盖最难的那些路径：多 Agent 编排、工具循环、反思收敛、预算熔断。
  这些路径在真实环境里很难稳定复现。
- 输入上下文与输出 schema 跟真实后端完全一致，所以"离线基线 vs 在线效果"成了一个受控实验。

代价是它必须被诚实标注：报告里直接写"离线确定性后端（不代表真实创作水平）"，
而且它的输出是由同一份结构化上下文渲染的模板化内容，不是模型推理。

---

## ADR-3 Agent 用两阶段，而不是一个大 ReAct 循环

决策：证据采集（一轮），然后是上下文收敛加结构化产出。

备选：经典 ReAct，边想边调工具，直到模型自己决定收尾。

否掉的理由：

1. 上下文污染。工具返回的原始 JSON 可能上百条字幕，连续塞进对话会稀释模型对最初任务目标的注意力。
2. 结构难保证。边调工具边吐 JSON，容易在半途返回缺字段的对象，把校验失败和工具循环纠缠在一起，问题定位困难。
3. 成本不可控。ReAct 的轮数由模型决定，批量生产时方差极大。

至于为什么是一轮采集而不是多轮：多轮采集的边际收益低，成本线性增长。
如果真需要多轮，正确的做法是拆成两个 Agent，本项目正是这么做的
（Analyst 理解素材，Critic 复核产出）。

## ADR-4 工具错误收敛为观测，不抛异常

决策：`ToolRegistry.invoke` 永远返回 `ToolResult`。

备选：让异常自然向上冒泡，由上层 try/except。

否掉的理由：Agent 的核心优势就在于"失败后能看到失败并调整"。
工具一报错就炸掉整条链，Agent 就退化成一个普通函数调用序列。
把 `{"ok": false, "error": "工具 'xxx' 不存在。可用工具：[...]"}` 回灌给模型，
它才有机会换参数、换工具，或者如实汇报做不到。

三类失败（工具不存在 / 参数不匹配 / 执行期异常）对模型都应表现为可读错误加建议。

## ADR-5 评测与生成解耦，评测器不调用模型

决策：`rubric.evaluate(variant, brief)` 是纯函数。

备选：把评分写进 Agent 的输出 schema 里一起产出。

否掉的理由：纯函数带来三个能力：

- 可以在不重新调用模型的情况下，对历史产物做回溯重评（改完权重直接重算）；
- 可以在 CI 里做精确断言；
- 可以被 `runner.rescore_variant` 单独复用。

---

## ADR-6 预算熔断优先于循环收敛

决策：调用次数 / token / 墙钟时间三重上限，任一耗尽即停止并如实标注。

备选：让循环一直跑到收敛为止。

否掉的理由：退化的循环可能无限调用模型。在真实业务里，超支比不完美更不可接受。
预算检查放在调用之前，避免"先超支后报错"，那样熔断就成了事后追认。

熔断时结果照常落盘并标注"结果可能未收敛"，而不是丢弃。

---

## ADR-7 降级必须显式，静默降级是缺陷

决策：关键帧抽取分三级（ffmpeg / manifest / synthetic），
每级都如实写入 `source` 与 `reason`，并一路带进报告。

备选：降级了就悄悄用替代方案，保持接口一致。

否掉的理由：静默降级比直接报错危险得多，
它会让基于合成占位的结论看起来像基于真实画面的结论。
所以合成分支返回 `available=False`，并在 `reason` 里写明"不可采信"。

同理，`SchemaGuard` 失败时返回 `data=None` 而不是半成品，
静默返回半成品数据比直接失败危险得多。

---

## ADR-8 续跑必须校验 brief 指纹

决策：`RunState.resumable(out_dir, brief)` 只在 `brief_fingerprint(brief)` 一致时返回状态。

备选：按 `run_id` 或目录存在性判断是否可复用。

否掉的理由：同一个目录里改完 brief 再跑，如果直接复用旧状态，产出的报告会与 brief 不符。
这种错误极难发现，因为报告本身看起来完全正常。

另外检查点是原子写入（写临时文件再 `replace`）：
直接覆盖写时进程被杀会留下破损 JSON，让续跑功能本身失效。

## 附：几个小但重要的决定

| 决定 | 理由 |
| --- | --- |
| 运行期零第三方依赖 | `pip install` 是评审者流失的最高频原因 |
| 用 `unittest` 而非 pytest | 承诺零依赖，就不能让第一次验证还需要装包 |
| 错误路径写成 `$.variants[0].hook` | JSONPath 形状，模型对它有很强先验 |
| 缺失必需字段的错误定位到字段本身 | 比定位到父对象更容易让模型一次改对 |
| `bool` 显式排除出 `integer` | Python 里 `bool` 是 `int` 子类，最经典的校验坑 |
| 权重和用断言校验 | 改权重忘同步会导致系统性偏移，但单点测试仍然全绿 |
| `trace.jsonl` 而非 JSON 数组 | 崩溃安全：完整行永远可读 |
| 提示词模板领域无关 | 避免某个类目的 brief 生成另一个类目味道的文案 |
